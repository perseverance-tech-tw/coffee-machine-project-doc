Coding Standard & Pattern Guideline

General coding rules​

  • Use the C++17 standard. Use modern features such as std::condition_variable, std::variant, and smart pointers.
  • Forbid raw pointers for object ownership (new/delete). Use std::unique_ptr for single ownership (e.g., in mediators) and std::shared_ptr only when shared ownership is strictly required.
  • Documentation — use the Doxygen standard for all header files. Mandatory tags: @brief, @param, and @return, so the API is self-documenting.
  • Performance — use multithreading to process heavy data such as AI inference.

Coding practices​

  • Modular design — each module has a clearly defined responsibility aligned with the system architecture.
  • Separation of concerns — functional layers remain isolated: UI layer, AI/vision processing, hardware integration, data management, and utility services.
  • Reusability — common functionality is implemented as reusable components (logging, signal handling, translation, gesture handling).
  • Minimal duplication — repetitive logic is refactored into shared modules or helper functions.
  • Clear interface design — modules communicate through well-defined interfaces to reduce coupling.
  • Maintainability — code is organized to support future enhancement, debugging, and testing.

Design patterns​

The patterns below are applied to the C++/GTK3 system running on the Kakip board (Renesas RZ/V2H) under Yocto Linux, referencing concrete project components.

Singleton​

Used for globally shared services that must have a single instance.

  • AI subsystem manager — manages execution of all AI models (YOLOv8s for cup-size detection, face models, landmark). Because inference uses the DRP-AI accelerator intensively, the singleton ensures the image-processing queue from the fisheye and front-facing cameras runs sequentially and NPU memory does not conflict.
  • ThreadController — manages parallel processing (C++ multithreading) and asynchronous work, keeping image preprocessing (OpenCV), AI inference, and UI updates on separate threads so the machine avoids lag (maintaining inference latency within target).
  • Database instance — manages single, secure access to the local SQLite database, preventing corruption from simultaneous read/write.

Factory / Registry​

Used for dynamic creation of UI pages.

  • PageRegistry for managing PageStack subclasses — in GTK3, the registry dynamically registers and instantiates UI subclasses for the touchscreen. Pages (Standby, Login Selection, Main Menu/Coffee Selection, Brewing Status, History, Settings) are loaded into memory only when requested by the navigation flow, keeping memory usage efficient.

Controller / Coordinator​

Separates UI logic from business and hardware logic, creating a conductor that orchestrates communication between software components and the physical Jura X10 base machine.

  • RootWindow as the main application controller — the bridge between the UI layer, AI processing layer, and control layer.
  • Brewing execution — when the cup size is classified and alignment is verified (within the ±1 cm tolerance under the nozzle), RootWindow passes the parameters to the brewing control, which adjusts water volume (oz/mL), extraction duration, and dosage to match the detected cup and user profile.

Wrapper / Helper​

Simplifies complex library interactions (GTKmm, OpenCV) into modular C++ functions.

  • SignalHelper — simplifies GTK3 event binding, translating touch actions (tapping "Brew", selecting strength, choosing a profile) into backend C++ execution.
  • GladeHelper — bridges XML-based GTK layouts to control logic, allowing UI elements (progress bar, volume indicators) to update dynamically without altering core logic.
  • SwipeHelper — handles swipe gestures.

Event-driven architecture​

The system responds to events generated by user interactions, sensor inputs, AI detection results, and system timers, ensuring responsive and efficient operation.

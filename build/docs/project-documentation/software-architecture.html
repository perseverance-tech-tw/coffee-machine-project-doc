Software Architecture Document (SAD)

info

This document reflects the actual implementation of the Smart Coffee Machine: a C++17 / GTK3 application targeting the Renesas RZ/V2H (Yocto Linux), with a fallback build for x86_64 development hosts.

Architectural overview​

The system follows a layered, modular architecture that separates user-interface concerns from application orchestration, AI/vision processing, hardware integration, and data persistence. Reusable AI/vision capabilities are packaged as independent libraries under module/, while the application itself lives under include/ and src/.

Architecture layers​

LayerLocationResponsibility
UI Layerinclude/pages/, src/pages/GTK3 screens and user interaction (40+ pages: standby, menu, customization, cup detection, brewing, settings, history, etc.).
Application / Orchestration Coreinclude/core/, src/core/Window setup, navigation, page lifecycle, thread management, camera multiplexing.
AI / Vision Processingmodule/Cup/face detection, fisheye undistortion, depth estimation, volume estimation, ArUco calibration, DRP-AI scheduling.
Hardware Integrationinclude/threads/, include/hardwares/Capture and detection threads, LDR sensor (GPIO), DMA buffers for DRP-AI inference.
Data Layerinclude/databases/, src/databases/SQLite persistence and per-entity controllers.
Utilitiesinclude/utils/, src/utils/Logging, signal/glade/swipe helpers, translation, image processing, screen utilities, virtual keyboard.

Key components​

ComponentResponsibility
RootWindow (core/root_window)Main application controller — initializes the window, navigation, and page stack, registers threads and sensors, and orchestrates the UI ↔ AI ↔ control interaction.
Navigation (core/navigation)Manages the navigation bar (back/center/right controls) and delegates user actions.
PageRegistry / PageRegistrar / PageStack (core/)Page lifecycle and factory system. Pages auto-register via the REGISTER_PAGE macro and are instantiated on demand, keeping memory usage efficient. PageStack is the base class with lifecycle hooks (init, connect_signals, on_page_changed, on_page_hidden).
ThreadController (core/thread_controller)Singleton registry of named std::thread objects (add / close / join).
CameraMultiplexer (core/camera_multiplexer)Singleton that manages Camera instances, sharing one physical source across multiple logical camera names (e.g., cup_cam, face_cam) and handling fisheye configuration.
Database + Controllers (databases/)Singleton SQLite facade composed of controllers: Coffee, User, FaceEmbedding, Preference, Brew, and Session.
AI Manager (module/detections … ai)Singleton that owns the detection components (face detector, cup detector, face aligner, ArcFace embedder, depth estimator) and shares AI resources across pipelines.
DRPQueue (module/detections … drp_queue)Thread-safe task queue that serializes inference on the DRP-AI hardware accelerator (DRP-AI is not safe for concurrent access).

Concurrency & threading model​

GTK runs the UI on the main (GLib) event loop. Long-running capture and inference work executes on dedicated background threads, synchronized with mutexes and condition variables:

ThreadRoleSynchronization
Main (GTK)UI rendering and event handlingGLib event loop
Face detectionCapture frames and run face detectionface_data_mutex + face_data_cv
Face recognitionAlign face, compute ArcFace embedding, match against the databaseshares the face lock data
Cup detectionDetect cup rim/body, run fusion (depth + ArUco + height), estimate volume, detect overflowcup_data_mutex + cup_data_cv
DRP-AI worker (V2H)Serialize hardware-accelerated inference callsDRPQueue (queue + mutex + condition variable)

Shared, single-instance services (ThreadController, CameraMultiplexer, AI, Database, DRPQueue) are implemented as singletons to coordinate access and prevent resource conflicts.

Design patterns​

The architecture applies several well-known patterns, each grounded in the codebase:

  • Singleton — globally shared services with a single instance: AI manager, ThreadController, CameraMultiplexer, Database, and DRPQueue. This guarantees a single, conflict-free access point to the DRP-AI accelerator, camera sources, and the SQLite database.
  • Factory / Registry — PageRegistry with the REGISTER_PAGE macro registers PageStack subclasses and instantiates pages by name, loading them into memory only when the navigation flow requires them.
  • Controller / Coordinator — RootWindow acts as the conductor between the UI, AI processing, and control layers, passing detected parameters (cup size, alignment) into the brewing control flow.
  • Wrapper / Helper — Camera and MoilUndistorter wrap GStreamer/V4L2 capture and the Moildev fisheye library; GladeHelper, SignalHelper, and SwipeHelper simplify GTK layout binding, signal connection, and gesture handling.
  • Observer / Event-driven — GTK signal connections and condition-variable notifications propagate user interactions, sensor inputs, AI results, and timer events, keeping the system responsive.
  • Producer–Consumer (task queue) — DRPQueue decouples inference requests from the single hardware executor.

Build configuration​

The project uses CMake and supports a dual build:

  • aarch64 (Renesas RZ/V2H) — compiled with -DV2H, enabling DRP-AI / MERA-TVM hardware-accelerated detectors.
  • x86_64 (development) — compiled with -DLINUX64, falling back to ONNX Runtime and TensorFlow Lite on CPU.

AI/vision modules build in dependency order (logger → moil → volume → detections → camera → aruco → overflow_detection), and GTK assets are embedded via GResource (assets.gresource.xml).
